# Design

## Context

See `proposal.md` for motivation. The current documentation toolchain and constraints that shape the
approach:

- `docs/` builds with Sphinx 9.2.0, MyST-Parser 5.2.0, Furo, sphinx-design, sphinx-copybutton, and
  sphinx-autobuild. The `docs` Hatch environment is Python-only; there is no CI and no Node.js
  prerequisite.
- The build runs with `-W --keep-going`, and `docs/develop/documentation.md` promises a local-only
  build and preview. Furo has a real light/dark toggle through `body[data-theme]`.
- The site has one real diagram, the package layers in `docs/develop/architecture.md`. The vault
  layout blocks in `docs/getting-started/first-vault.md` and `docs/reference/vault-format.md`, and
  the output block in `docs/guide/command-line.md`, are literal text rather than diagrams.
- `sphinxcontrib-mermaid` 2.1.1 is the current stable release. Its default HTML output is `raw` and
  loads Mermaid from jsdelivr; `mermaid_use_local` can point at a local ESM runtime under
  `html_static_path`. Its `install_js` hook skips pages that contain no Mermaid node.
- Mermaid 11.12.1 publishes an ESM entry plus `chunks/mermaid.esm.min/`. The tree without source maps
  is 74 files, about 2.6 MB on disk and roughly 0.77 MB compressed in git.
- `tests/docs/test_style.py` already parses `docs/**/*.md` with `markdown-it-py` and enforces
  emoji-prefixed headings and `tl;dr` summaries.

## Goals / Non-Goals

**Goals:**

- Render the architecture diagram from Mermaid source with no network access at build time or page
  load.
- Keep `hatch run docs:build` and `docs:serve` Python-only and cross-platform.
- Make the diagram readable on narrow screens and correct in both Furo themes.
- Give authors a clear convention for when a Mermaid diagram is appropriate, and make the convention
  testable.
- Keep the documentation site's existing visual language: no new custom CSS and no new admonition.

**Non-Goals:**

- Build-time SVG or PDF output. That path would add Node.js, mermaid-cli, and Chromium to the docs
  build, and it would need a separate light and dark image variant.
- Converting directory trees or command output to diagrams.
- A general diagrams library, a diagram index, or a second diagram in this change.
- Changing application behavior, runtime dependencies, the vault format, or the public Python API.

## Decisions

### Client-side raw rendering with a vendored runtime

Use `sphinxcontrib-mermaid==2.1.1` with `mermaid_output_format = "raw"` and
`mermaid_use_local = "vendor/mermaid/mermaid.esm.min.mjs"`. Vendor the unmodified Mermaid 11.12.1 ESM
tree under `docs/_static/vendor/mermaid/`.

Rationale:

- It keeps the build and preview fully offline and Python-only. The existing docs prerequisites stay
  valid on Linux, macOS, and Windows.
- The runtime is static JavaScript, so it is platform-independent; no browser automation or native
  toolchain is involved.
- Furo's `body[data-theme]` toggle is observed by the extension, which re-runs Mermaid with the
  matching light or dark theme.
- The extension injects its script only on pages that contain a Mermaid node, so the rest of the site
  does not download the runtime.
- Plain fences stay readable in the Markdown source and render natively on GitHub.

Alternatives considered:

- **Build-time SVG with `mermaid_output_format = "svg"` and `mmdc`.** Rejected for this change: it
  adds Node.js 22+, mermaid-cli, and a headless Chromium to `hatch run docs:build`, and the extension
  emits one baked theme. It can be revisited if print/PDF or a hard syntax gate becomes a
  requirement.
- **Committed SVG generated by an opt-in script.** Rejected because it adds a manual regeneration
  step, two theme variants, custom CSS, and a staleness risk for one diagram.
- **CDN runtime.** Rejected because it violates the local-assets promise and makes a local docs
  preview depend on the network.
- **Graphviz.** Rejected because it is not Mermaid, and it still adds an external binary to the build.

### Plain fences with MyST directive mapping

Set `myst_fence_as_directive = ["mermaid"]` and write plain ` ```mermaid ` fences instead of
`{mermaid}` directives. This keeps the same source renderable by GitHub and by Sphinx, and avoids a
second syntax in the Markdown.

Accessibility metadata goes inside the diagram as Mermaid's `accTitle` and `accDescr`, which produces
an accessible SVG title and description. The style test requires both lines so a diagram cannot be
added without them.

### Vendor the upstream distribution, not a custom bundle

Copy the `dist/mermaid.esm.min.mjs` entry and `dist/chunks/mermaid.esm.min/` tree verbatim, without
`.map` files. Add the upstream `LICENSE` and a short `README.md` that records the version, source URL,
and the replacement procedure.

Rationale:

- A verbatim vendor tree is auditable and matches the upstream release.
- A custom single-file bundle would need its own bundler and a second build process for upgrades.
- The tree is only 0.77 MB compressed in git; the existing screenshots are 264 KB, so the growth is
  acceptable for an offline-capable renderer.
- The extension will move to a bundled runtime in its 3.0 line; when that release is available, the
  vendor tree can be removed without changing the page source.

### Keep literal trees and output as text

Only `docs/develop/architecture.md` changes its rendering. Directory trees and command output stay in
`text` fences because readers copy them verbatim, and a graph would remove the literal spelling.

### Test the convention, not the Mermaid parser

There is no Python Mermaid parser, so the build cannot validate diagram syntax. The style test covers
the parts that can be checked deterministically:

- no `+---+` box art in fenced blocks;
- every `mermaid` fence contains `accTitle:` and `accDescr:`;
- the vendored entry module and at least one chunk exist, and the configured runtime path is local.

Syntax and layout are verified by opening the architecture page with `hatch run docs:serve` in both
themes. If visual verification proves insufficient, the fallback is the build-time SVG path, not a
second linter.

### Build settings

- Keep `mermaid_output_format = "raw"` explicit, so a future change cannot switch the build to
  mermaid-cli by accident.
- Set `mermaid_height = "auto"`; the extension's default is a fixed 500 px, which leaves unnecessary
  space around a small graph.
- Keep the extension's default light and dark themes rather than declaring custom colors.
- Keep `mermaid_version = "11.12.1"` aligned with the vendored tree for readers, even though the
  local runtime path takes precedence.

## Risks / Trade-offs

- **`sphinxcontrib-mermaid` 2.1.1 predates Sphinx 9.2.0 by about seven weeks.** → Make the extension
  install and a warning-free `hatch run docs:build` the first verification task. If it is
  incompatible, stop and choose a compatible release or the SVG fallback rather than weakening `-W`.
- **The default behavior loads Mermaid from a CDN.** → Set `mermaid_use_local` explicitly and assert
  the local path in the docs style test.
- **A malformed diagram is not a build failure.** → Require `accTitle`/`accDescr`, review the page in
  `docs:serve` in both themes, and treat repeated diagram errors as the trigger to adopt build-time
  SVG.
- **The vendor tree adds 74 files and about 2.6 MB on disk.** → Exclude source maps, add the license
  and version note, and keep the tree isolated under one directory. Remove it once the extension's
  3.0 line ships a bundled runtime.
- **A wrong static path fails only in the browser.** → Assert the entry module and chunks exist in
  the docs style test; a broken import then fails a local test before it fails a reader.
- **No-JS readers and future print/PDF output see the Mermaid source.** → Accept for the current
  HTML-only site; record build-time SVG as the migration path when printing becomes a requirement.
- **Vendored JavaScript is a supply-chain surface.** → Pin the exact Mermaid version, keep the
  upstream license, and update the version, source URL, and runtime together.
- **The diagram's auto-layout may change between Mermaid versions.** → Pin the runtime and review the
  architecture page after any vendor update.

## Migration Plan

There is no deployed site and `docs/_build/` is gitignored, so there is no data or URL migration.
Apply the dependency, configuration, vendor tree, page change, documentation, and tests in one
coherent change, then verify `docs:build`, the style test, `hatch check`, and the full test suite.
Rollback is a revert of the docs dependency, `conf.py`, vendor tree, page, guide, tests, and changelog
entry; no application state is involved.
